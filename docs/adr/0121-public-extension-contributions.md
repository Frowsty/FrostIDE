# ADR 0121: Public extension contribution API and local debug adapters

Status: source implementation and regressions authored; independent source review pending; execution deferred.

UX-20 exposes a versioned public **data** API through `frost/lang/extension_manifest.hpp` and Workbench's `setExtensionCatalog`, `extensionCatalogState`, `executeExtensionCommand` and `debugWithExtension`. The catalog is the application-only executing setting `extensions.catalog`. A project cannot introduce executable contributions. No native library, JavaScript or Lua plugin code is loaded into the IDE; no installer, marketplace, hooks, network service or package download is introduced. Existing specialized language/debug integrations retain their own routes.

API v1 requires integer `apiVersion: 1` and at most 32 `extensions`. Each contribution requires a unique lowercase alphanumeric/hyphen `id`, nonempty `name` and declared `version`, boolean `enabled`, an explicit `capabilities` array and a `contributes` object. Supported grants are exactly `languages`, `commands`, `debugAdapters`; unknown or duplicate grants and contribution families refuse. The complete catalog is bounded to 1 MiB. Declared versions remain user metadata, never evidence of observed tool version.

- `contributes.languageServers` uses the exact ADR0117 descriptor contract. Enabled packages compose atomically with the personal language registry. Server ID/selector collisions refuse, never silently override. Each server launches lazily only for an admitted document; real initialize capabilities and serverInfo govern semantics. Actual grammar support (ADR0119) is independent of whether a language server is configured.
- `contributes.commands` entries require local `id`, `title`, `serverId`, provider `command` and JSON-array `arguments`. An explicit user action selects `package-id/local-id`. The current document's admitted active provider must have that exact server ID and advertise the exact command in its actual `executeCommandProvider.commands`. The request crosses the retained registry authority and incoming applyEdit validation; no manifest fabricates a semantic command.
- `contributes.debugAdapters` entries require local `id`, `title`, `adapterId`, `tool` and JSON-object `launch`. `tool` deliberately reuses the ADR0117 descriptor, extensions, exact executable/artifact/license pins and existing SPDX allowlist. A selected adapter receives its literal stdio arguments and the configured launch object through the real existing DAP controller/client/session. API v1 offers explicit launch of the current saved source, never attach. The adapter's DAP response supplies real debugger capabilities; no unavailable adapter is simulated. Program arguments, interpreter/runtime selection and vendor-specific launch fields remain the user's reviewed adapter configuration.

Only JSON value placeholders `${file}` and `${workspaceFolder}` expand, bounded to depth 32 and 32768-byte strings. Inserted paths remain literal data; there is no shell, environment, command or executable interpolation. For example, a command arguments array can be `["${file}"]`; an adapter launch object can be `{"program":"${file}","cwd":"${workspaceFolder}"}` when that actual adapter accepts those fields. A reviewed descriptor must use absolute local paths and real file SHA256 values, including all interpreter/tool payloads that the user wishes pinned. Pins prove named bytes, not their origin, license accuracy, dynamic imports, child processes or hermetic execution. Local tools run with ordinary user process authority; ordinary descriptors provide process isolation from the IDE. The explicit sandbox profile below adds a separate native rights boundary.

Configure Extension Contributions opens an import/review editor; Run Extension Language Command and Debug Current File With Extension Adapter are command-palette product actions. Import merely reads bounded local JSON. Acceptance validates the entire aggregate before persisting. Removal/configuration/workspace/trust/physical identity changes cancel command observations and stop a debug session only when its controller generation belongs to this contribution. Old registry launchers revoke immediately and refuse retained work. Physical project replacement requires close/reopen (or observed trust withdrawal) before debug admission; unrelated trust revisions cannot revive the replaced physical identity. Debug launch saves via the ordinary Save path. A cancellable worker captures source SHA256, verifies pins and creates the actual child; the GUI adopts only a current contribution generation, unchanged clean editor version and matching source metadata under retained workspace authority. The DAP writer rechecks exact source bytes and authority immediately before actual launch transmission. No large artifact hash or child creation runs on GUI adoption. The actual controller still owns DAP transport, breakpoints, threads, stepping, variables and shutdown.

LTR-18 now has actual syntax grammars for Python, JavaScript/JSX, TypeScript/TSX, YAML, TOML and PowerShell, plus the existing language profiles. Semantics and debugging for these languages are conditional on explicit real installed providers/adapters. No Python interpreter, JavaScript runtime, PowerShell runtime, LSP or DAP binary is bundled or downloaded. No executable extension scripts, arbitrary IDE object access, custom UI contributions, marketplace, compatibility with third-party plugin APIs or dynamic LSP registration are claimed. Acceptance on Windows/Linux, query compilation, actual installed-provider semantics and vendor DAP launch are deferred until the user authorizes execution. Authored fixtures cover API negotiation, capability grants, collisions, exact argument expansion, advertised commands, license refusal, revocation and product persistence/refusal; they are not runtime acceptance evidence.

## Opt-in read-only stdio sandbox and real sample

An optional ADR0117 descriptor `sandbox` object has exactly `profile: "read-only-stdio"` and nonempty `files`. Every file requires an absolute `path` already named in the descriptor's reviewed artifact pins, a unique safe relative staging `relativePath`, and an explicit boolean `executable`. The executable must have an execute grant. No recursive ambient runtime discovery, write/network grant, or manifest-chosen container/staging identity exists in this profile. Unknown grants refuse. Existing unsandboxed descriptors and specialized LSP/DAP launches retain their permissions.

The registry's launch worker supplies a clean environment, stdio pipes, kill-on-close tree containment and a native `ProcessSandboxProfile` with exact read/execute paths and network denied. Windows captures and rechecks SHA256 for every explicitly pinned staged file, bounded to 128 MiB each/256 MiB aggregate. The native helper creates a new private generation under the application settings profile, derives its own container identity and remaps exact executable/script arguments; no original tool/project ACL is modified. Linux receives exact original path grants and native enforcement must either succeed or return its actual capability error. No network or filesystem permission failure retries an ordinary launch. Private staging generations are retained for later safe collection; this slice does not delete in-use content.

Native enforcement is authored by the coordinated IO sandbox owner and remains unexecuted. Capability/error behavior, kernel and Windows policy availability, ambient system rights and the final paired enforcement commit must be source-reviewed before claiming this boundary complete. The public profile only implements the stated read/execute stdio scope, not arbitrary extension permissions or debugger target child/write rights. Unsupported enforcement is an explicit launch failure; normal generic tool permissions are unchanged.

`examples/extensions/text-statistics` is an actual source-built bounded stdio LSP and offline manifest preparer, not a mocked semantic service. It advertises and executes `frost.sample.statistics` against real received buffers. The opt-in future `FROST_BUILD_EXTENSION_SAMPLE` target and app onboarding fixture load its generated capability-declared manifest through normal Workbench onboarding and the native sandbox, observe actual serverInfo and exact returned counts, then withdraw the contribution. Required runtime libraries must be explicit, approved and pinned. No sample execution, OS enforcement probe, configure/build or test execution occurred during authoring. The existing palette editor imports/reviews the generated local manifest; there is no sample special-case launch bypass.
