# Fix in Scope

`code.fixInScope` runs the active project's real clang-tidy inspection profile for File, Directory, Target or Project. Headers are analyzed through the compilation database's translation units. Target matching uses the existing inspection scope resolver and the actual database; missing translation units explicitly refuse.

Preparation captures project source/header/configuration bytes and open-buffer text before launching the tool. A private, owned scratch directory holds a copy of the compilation database, a Clang VFS overlay of captured images, and the fresh `--export-fixes` YAML output. The helper's LLVM YAML decoder preserves raw primary and note replacement groups, including overlaps. Diagnostic prose is never converted into edits, and `-fix` is never sent.

The supported command profile requires absolute working directories. Explicit project-local include directories and forced include files additionally capture otherwise excluded inputs read-only, including generated and extensionless files. Already captured editable source/header images retain their editability. Unexpanded response files, PCH/module input options and compiler driver configuration files explicitly refuse. System SDK/library trees outside the project remain toolchain inputs, rather than editable project snapshots. Linked project trees, ambiguous physical aliases, unreadable inputs and capture-budget overflow refuse. This is a bounded active-compilation-database profile, not universal toolchain hermeticity.

Preview contains the complete supported replacement set. Several alternative fixes, overlapping edits, uncaptured targets or edits to read-only compiler inputs refuse the entire proposal. The UI reports diagnostics with no exported automatic fix separately. Apply uses one existing RefactoringCoordinator transaction for all open and closed files. Request generation, trust, provider/database, tool settings, open buffers, physical identities, source namespaces and captured bytes are rechecked before preview and at Apply. External changes require a fresh preparation. One global Undo/Redo owns the accepted edit.

Source-only implementation: authored domain, real LLVM YAML/clang-tidy VFS, and Workbench stale-preview/atomic Undo tests have not been executed under the implementation-first instruction. Future execution requires the existing pinned LLVM tools (`frost-clang`, clang-tidy and the configured Clang compiler); absent tools are failures, not silently skipped fixtures.
